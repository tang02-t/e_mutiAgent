# 基于多智能体协作的电力变压器故障诊断系统技术报告

**项目名称**：transformer-diagnosis-agent
**版本**：dev
**报告日期**：2026-06-15

---

## 摘要

本系统是一个面向电力变压器故障诊断的**多智能体（Multi-Agent）协作系统**。系统将"运维人员提出变压器异常问题 → 自动诊断并输出处理建议"这一专家决策过程，解构为 **Planner（规划）、Retriever（检索）、Generator（生成）、Validator（验证）** 四个职责单一的智能体，并以 **LangGraph** 进行图式编排，构建出一条带"质量验证—返工迭代"闭环的诊断流水线。

系统融合三类核心技术能力：

1. **检索增强生成（RAG）**：基于 Milvus 向量库 + DashScope Embedding 的父子分块检索，从 100+ 篇变压器故障专业文献中召回领域知识；
2. **贝叶斯网络故障归因**：依据 DL/T 722-2014《变压器油中溶解气体分析导则》，结合三比值法与朴素贝叶斯推理，对 8 类典型故障给出概率排序；
3. **时序预测与异常检测**：基于 ETT 数据集，用线性回归实现油温预测与 3σ 异常检测。

本报告系统阐述系统架构、各智能体实现细节、工具层算法原理、状态管理机制、数据体系与验证方法。

## 1. 系统架构

### 1.1 总体架构

系统采用**分层 + 流水线**架构：

```
┌─────────────────────────────────────────────────────────────┐
│                       用户查询层                               │
│             (变压器故障描述 / DGA数据 / 设备上下文)             │
└──────────────────────────────┬──────────────────────────────┘
                               │
┌──────────────────────────────▼──────────────────────────────┐
│                   智能体编排层 (LangGraph)                     │
│   Planner ──→ Retriever ──→ Generator ──→ Validator          │
│                                  ▲____________│ (迭代反馈)      │
└──────────────────────────────┬──────────────────────────────┘
                               │
┌──────────────────────────────▼──────────────────────────────┐
│                    工具能力层 (MCP Client)                     │
│  rag_search │ fault_attribution │ ett_forecast │ ts_anomaly  │
└──────────────────────────────┬──────────────────────────────┘
                               │
┌──────────────────────────────▼──────────────────────────────┐
│                       基础设施层                               │
│  Milvus向量库 │ DashScope LLM/Embedding │ ETT数据集 │ 知识库  │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 工作流编排（LangGraph）

核心工作流定义于 `src/graph/workflow.py`，采用 LangGraph 的 `StateGraph` 构建有向图：

```
START → planner → retriever → generator → validator → [条件路由]
                                              ↑              │
                                              └──────────────┘
                                          (verdict=REVISION)
```

**节点与边定义**：

```python
graph.add_edge(START, "planner")
graph.add_edge("planner", "retriever")
graph.add_edge("retriever", "generator")
graph.add_edge("generator", "validator")
graph.add_conditional_edges(
    "validator", _route_after_validator,
    {"generator": "generator", "END": END}
)
```

**条件路由逻辑**（`_route_after_validator`）：

| Validator 判定 | 路由目标 | 说明 |
|----------------|----------|------|
| PASS（score≥7） | END | 诊断质量合格，直接输出 |
| REVISION（score 4-6）且未达迭代上限 | generator | 携带改进建议返工重生成 |
| REVISION 且已达 `max_iterations`(默认3) | END | 接受当前结果并附系统提示 |
| FAIL（score<4） | END | 质量不达标，输出失败提示 |

**降级机制**：当 LangGraph 未安装时，自动降级为 `_run_sequential_workflow()` 串行执行（不支持迭代），保证系统鲁棒性。

### 1.3 多模型配置

系统支持**每个智能体独立配置不同 LLM**（`config.yaml` 的 `llms` 节点），通过 `get_llm_config()` 实现"指定智能体配置 > default 配置"的优先级回退：

| 智能体 | 模型 | 温度 | max_tokens | 设计考量 |
|--------|------|------|-----------|----------|
| Planner | qwen3.5-35b-a3b | 0.2 | 2048 | 规划需较强推理 |
| Generator | qwen3.5-35b-a3b | 0.1 | 2048 | 生成需稳定准确 |
| Validator | qwen3.5-35b-a3b | 0.1 | 1024 | 评估需严格一致 |
| Retriever | —（无需 LLM） | — | — | 纯工具编排 |

## 2. 智能体实现细节

### 2.1 状态管理（AgentState）

所有智能体通过共享的 `AgentState`（`src/graph/state.py`）数据类传递信息，这是多智能体协作的核心载体：

```python
@dataclass
class AgentState:
    user_query: str                          # 用户输入
    context: Dict[str, Any]                  # 设备上下文
    plan: Optional[str]                      # Planner 输出
    retrieved_knowledge: List[Dict]          # Retriever 知识库命中
    tool_calls: List[Dict]                   # 工具调用记录
    draft_answer: Optional[str]              # Generator 草案
    validation_report: Optional[str]         # Validator 报告
    validation_verdict: str                  # PASS/REVISION/FAIL
    revision_feedback: Optional[str]         # 改进建议（供返工）
    iteration: int                           # 当前迭代轮次
    max_iterations: int                      # 迭代上限
    reasoning_trace: List[Dict]              # ReAct 推理轨迹
    final_answer: Optional[str]              # 最终结果
    next_node: str                           # 路由标记
```

`reasoning_trace` 记录完整的 ReAct（Reasoning + Acting）轨迹，实现诊断过程的可追溯性。

### 2.2 Planner（规划智能体）

**职责**：意图分析 + 任务规划 + 工具决策。

**实现**（`src/agents/planner.py`）：
- 调用 LLM 生成结构化 JSON 计划，包含 `intent_analysis`（意图分析）和 `steps`（3-6 步诊断流程）；
- 每个 step 包含 `id / stage / description / tool / arguments`，其中 `tool` 字段指明该步需调用的工具；
- 使用统一的 `parse_llm_json()` 解析（自动处理 `<think>` 标签与 markdown 包装）；
- 将结构化计划同时写入 `state.reasoning_trace`（供 Retriever 读取）和 `state.plan`（可读文本）。

**容错**：LLM 不可用或解析失败时返回空计划，触发下游 Retriever 的 fallback 模式。

### 2.3 Retriever（检索智能体）

**职责**：根据 Planner 计划编排并执行工具调用。**本智能体不调用 LLM**，是纯工具编排器。

**核心机制**（`src/agents/retriever.py`）：

1. **并行执行**：使用 `ThreadPoolExecutor` 对独立工具（`rag_search` / `timeseries_anomaly` / `ett_forecast`）并行调用，并发数由 `workflow.parallel_tools`（默认 3）控制；

2. **依赖编排**：`fault_attribution` 在缺少 DGA 数据时需要 RAG 结果作为上下文，故被识别为"依赖任务"，在并行阶段（RAG）完成后串行执行，并注入 `_rag_context`；

3. **Fallback 模式**：当 Planner 未产出结构化计划时，退化为固定工具集（`rag_search` + `timeseries_anomaly`）。

```python
# 两阶段执行：先并行独立工具，再串行依赖工具
results, kb_results_acc = self._execute_tools_parallel(independent_tasks, state)
for task_info in dependent_tasks:   # fault_attribution 等
    self._execute_single_tool(...)
```

### 2.4 Generator（生成智能体）

**职责**：综合所有证据生成面向运维人员的诊断结论与处理建议。

**实现**（`src/agents/generator.py`）：
- `_extract_tool_results()` 从 `tool_calls` 中提取并格式化四类证据：知识库片段、时序分析、故障归因、油温预测；
- **首次生成** `_llm_generate()` 与**返工生成** `_llm_revision()` 使用不同 system prompt，返工时额外传入 `revision_feedback` 与 `previous_draft`；
- **三级降级**：LLM 生成 → LLM 返回空则降级模板 → LLM 异常则降级模板（`_template_generate()`）。模板内置基于 GB/T 7252 的标准检查项（DGA、红外热成像、电气试验等）。

**知识片段格式化**兼容多种检索后端结构（本地 txt / Milvus 父子分块 / 扁平结构），增强适配性。

### 2.5 Validator（验证智能体）

**职责**：对诊断草案进行结构化质量评估，并驱动迭代闭环。

**实现**（`src/agents/validator.py`）：
- 输出结构化 `ValidationResult`：`verdict / score(0-10) / strengths / weaknesses / improvement_suggestions / summary`；
- **评估维度**：与用户问题相关性、是否充分参考检索知识、逻辑/安全风险、是否符合电力安全规程；
- **判定规则**：PASS(≥7) / REVISION(4-6) / FAIL(<4)；
- **规则降级** `_rule_validate()`：LLM 不可用时基于关键词（安全/保护/建议）与内容长度打分；
- **闭环驱动**：REVISION 时将 `improvement_suggestions` 写入 `state.revision_feedback`，路由回 Generator；达到迭代上限时接受当前草案并附系统提示。

为避免上下文膨胀，迭代时仅回传"上一轮改进建议"（`last_improvement_suggestions`）而非整份报告。

## 3. 工具层算法原理

### 3.1 RAG 检索引擎

**实现**（`src/tools/rag_engine.py`）：基于 Milvus（Zilliz Cloud）+ DashScope `text-embedding-v4`。

**父子分块检索**（核心创新）：

```
① 仅在 child 子块中做向量检索（精确定位段落）
        ↓ expr='chunk_type == "child"'
② 收集命中子块的 parent_id，批量查询 parent 父块
        ↓ expr=f"chunk_id in {parent_ids}"
③ 组装返回：子块（精确命中）+ 父块（完整章节上下文）
```

此设计兼顾**检索精度**（子块粒度小、命中准）与**上下文完整性**（父块提供完整章节），并支持图文混排（`image_paths` 字段）。检索参数：`metric_type=L2`，`nprobe=10`，`top_k=5`。

### 3.2 贝叶斯网络故障归因（核心算法）

**实现**（`src/tools/fault_attribution.py`），依据 **DL/T 722-2014** 标准。

**网络结构**：故障层（8 类）→ 征兆层（14 类）的有向无环图，朴素独立近似。

**8 类故障**：绕组变形、绕组匝间短路、铁芯多点接地、套管故障、分接开关故障、局部放电、过载过热、绝缘老化。

**推理流程**（四步）：

**Step 1：DGA 三比值法编码**（表6）
对三个特征比值进行离散编码：

| 比值 | 编码规则 |
|------|----------|
| C₂H₂/C₂H₄ | <0.1→0, [0.1,3)→1, ≥3→2 |
| CH₄/H₂ | <0.1→1, [0.1,1)→0, ≥1→2 |
| C₂H₄/C₂H₆ | <1→0, [1,3)→1, ≥3→2 |

编码组合匹配表7故障判据（如"电弧放电"=[1,*,*]→绕组短路/套管/分接开关）。

**Step 2：朴素贝叶斯后验推理**

$$P(F_i \mid E) \propto P(F_i) \cdot \prod_{e_j \in E} P(e_j \mid F_i)$$

其中先验 $P(F_i)$ 来自 `_PRIOR_PROBS`，似然 $P(e_j \mid F_i)$ 来自人工标定的条件概率表（CPT），随后归一化。

**Step 3：规则与贝叶斯融合**

$$P_{fused} = 0.7 \cdot P_{bayes} + 0.3 \cdot P_{rule} \quad (\text{有规则匹配时})$$

**Step 4：排序生成报告**，输出故障概率排序、严重程度分级（高/中/低风险）、DGA 特征解释。

**注意值自动推断征兆**（DL/T 722）：H₂>150、CH₄>120、C₂H₂>5、C₂H₄>50、C₂H₆>65 μL/L 时自动置位对应 evidence。

### 3.3 ETT 油温预测

**实现**（`src/tools/ett_forecasting.py`）：

- **模型**：6 维负载特征 [HUFL, HULL, MUFL, MULL, LUFL, LULL] → 油温 OT 的线性回归；
- **求解**：正规方程 $\theta = (A^TA + \lambda I)^{-1}A^Ty$（带 1e-6 岭正则，奇异时退化为伪逆）；
- **滚动预测**：以最新窗口状态做 horizon 步滚动预测，引入均值回归 $\hat{OT} = 0.9 \cdot pred + 0.1 \cdot OT_{prev}$ 防止温度漂移；
- **配置**：默认 lookback=96、horizon=24、train_window=168（参考 Informer 论文）。

### 3.4 时序异常检测

**实现**（`src/tools/timeseries.py`）：基于 3σ 规则，$|v - \mu| > 3\sigma$ 判定为异常点。当前为简化版示例，可对接 DCS/历史数据库。

### 3.5 MCP 工具客户端

**实现**（`src/tools/mcp_client.py`）：极简 MCP 风格客户端，通过 `register_tool(name, fn)` 注册工具，`call_tool(name, *args)` 统一调用，实现工具与智能体的解耦。

## 5. 系统验证方法

系统验证分为**两个独立层次**：

### 5.1 故障归因引擎评测（确定性）

**脚本**：`scripts/eval_fault_attribution.py`（无 LLM/网络依赖，秒级出结果）。

**指标体系**：Top-1 准确率、Top-3 命中率、各类 Precision/Recall/F1、Macro/Weighted-F1、混淆矩阵、**分严重程度召回率**（安全底线指标）。

**基线结果**（3000 条模拟数据）：

| 指标 | 数值 |
|------|------|
| Top-1 准确率 | 37.9% |
| Top-3 命中率 | 88.5% |
| Macro-F1 | 0.229 |
| critical 故障召回 | 100% |
| serious 故障召回 | 32% |

**关键洞察**：Top-3 高（88.5%）证明数据特征与故障强相关；Top-1 偏低源于贝叶斯网络 CPT 为人工近似值（likelihood 连乘偏向高产气故障）。**这为用真实标注数据校准 CPT 提供了直接的量化依据。**

### 5.2 端到端多智能体评测

**脚本**：`scripts/eval_end2end.py`，采用可注入工具设计（真实归因引擎 + 可选 mock/真实 RAG + 真实 LLM），支持离线流程测试与在线诊断评测。

**指标体系**：流程完成率、主故障命中率、关键要点覆盖率、**安全合规率**、Validator 平均得分、平均迭代轮次、LLM 降级率。

**验证结论**：评测框架完整跑通（完成率 100%）。当前 `config.yaml` 中 DashScope API Key 免费额度耗尽（HTTP 403 FreeTierOnly），导致 LLM 全部降级为规则模式——这一现象被框架准确捕获并报告（LLM 降级率 100%），说明评估系统真实诊断能力前需先解决 LLM 配额问题。

## 7. 创新点总结

本系统在工程实现与领域结合层面具有以下创新点：

### 创新点 1：诊断专家决策的多智能体解构与闭环编排

将变压器故障诊断这一复杂专家决策过程，解构为"规划—检索—生成—验证"四个职责单一的智能体，并以 LangGraph 构建带条件路由的状态图。区别于传统单一 LLM 的"一问一答"，本系统通过 **Validator 三级判定（PASS/REVISION/FAIL）驱动 Generator 迭代返工**，形成质量自检与自我修正闭环，显著提升诊断结论的可靠性与专业性。

### 创新点 2：贝叶斯网络 × 三比值法的混合故障归因

将国标 DL/T 722-2014 的**三比值法编码规则**与**朴素贝叶斯后验推理**有机融合：先用三比值法对 DGA 气体进行离散编码并匹配故障判据，再用贝叶斯网络计算各故障后验概率，最后以 $0.7P_{bayes}+0.3P_{rule}$ 加权融合。这种"规则可解释 + 概率可量化"的混合范式，既保留了行业标准的权威性，又提供了概率化的故障排序与置信度，弥补了纯规则法无法量化、纯数据驱动法缺乏可解释性的不足。

### 创新点 3：父子分块的检索增强机制

RAG 引擎采用**父子分块（Parent-Child Chunking）**：向量检索仅在细粒度子块上进行以保证命中精度，命中后通过 `parent_id` 展开父块完整章节作为上下文。该机制同时解决了"小块检索精度高但上下文不全"与"大块上下文全但检索噪声大"的矛盾，并原生支持图文混排（`image_paths`），契合变压器文献中大量含图表的特点。

### 创新点 4：多源异构证据的统一融合诊断

系统将三类异构信息源——**非结构化知识（RAG 文献）、结构化推理（贝叶斯归因）、时序数据（油温预测/异常检测）**——通过统一的 `AgentState` 与工具结果格式化层汇聚，由 Generator 综合生成诊断。这种多模态证据融合更贴近真实运维专家"查资料 + 看数据 + 凭经验"的综合判断方式。

### 创新点 5：全链路降级与多模型差异化配置的工程鲁棒性

- **全链路降级**：每个环节（LangGraph→串行、LLM→模板/规则、Planner 空计划→Retriever fallback、Milvus→mock）均设计了 fallback 路径，保证任一外部依赖失效时系统仍可运行；
- **per-agent 多模型配置**：支持为不同智能体（规划/生成/验证）独立配置 LLM 与超参数，实现推理能力与调用成本的精细化权衡。

### 创新点 6：分层可量化的验证体系

设计了**确定性归因评测 + 端到端系统评测**两层验证框架，并引入**分严重程度召回率**作为安全底线指标。该体系不仅能量化系统效果，更能精准定位薄弱环节（如本项目据此发现"贝叶斯 CPT 需用真实数据校准"），为系统持续迭代提供数据驱动的依据。
